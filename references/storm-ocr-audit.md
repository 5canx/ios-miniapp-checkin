# 影视飓风：8 次与 11 次 OCR 的逐次追溯

本报告只读取已经回传的私有运行文件，没有重新执行影视飓风。业务源码行号固定到提交 `97c9364`；本次 0.4.3 没有修改业务运行器，下面同一源码中的行号仍一致。实际记录不包含原生调用栈，函数路线由功能块、观察时间/区域、步骤工具计数与源码对应，不能称为运行时栈采样。

## 计数口径

- 最终记录 `35b960651cb943869c4089d3d976ebc9`：9 块，`ocr_screen` 实际 8 次、14.423s，整段 31.643s，首页起点，悬浮球开启，当日已签到。
- 中间记录 `ae90ef9dfafd45ab8a660423b7f1d287`：9 块，实际 11 次、16.614s，整段 35.104s，也是首页起点。这是合并输入回读、调整过渡等待之前的运行，不是当前流程又固定执行了 11 次。
- 两者分别保存 8/11 个独立页面观察，本例恰好与调用数一致；一般页面会去重，**不能用页面数量代替 OCR 调用数**。统计以同一 run_id 的 `flow_step_completed.device_tools.ocr_screen.calls` 求和并与结束状态核对。
- 8 次运行：步骤 1=4 次，2=1 次，3–6=0 次，7=1 次，8=1 次，9=1 次。11 次运行仅步骤 1 增至 7 次，其余相同。
- “一次跑完”可以给出这条成功路径的正常预算 8 次，无法证明网络、登录变化和所有异常分支的绝对最大值。不得为了寻找最大值重复实机运行；用源码有界分支分析异常开销。

## 实际共用的 OCR 发起位置

本例真正向 OCR 发出请求的 `CNTaskScreen` 源码表达式只有两处：

1. [CNTaskScreen.m:70](https://github.com/5canx/autodam/blob/97c9364/Sources/CNTaskScreen.m#L70)：`refreshRegion:`，同区域缓存无效才调用局部 OCR。
2. [CNTaskScreen.m:88](https://github.com/5canx/autodam/blob/97c9364/Sources/CNTaskScreen.m#L88)：`refreshWithObservation:scoped:`，没有可用观察时调用全屏 OCR。`refresh` / `reuseOrRefresh` / `after` 最终汇入这里。

共同传输是 [CNMCP.m:94](https://github.com/5canx/autodam/blob/97c9364/Sources/CNMCP.m#L94) 的 `call:arguments:` → `tools/call`。后续 `textIn:`、`has`、页面状态判断、签到回执解析均读取已经得到的数组，不各自再发 OCR。暂停恢复时 [CNBridge.m:135](https://github.com/5canx/autodam/blob/97c9364/Sources/CNBridge.m#L135) 可额外发起一次检查；本次两条业务记录没有暂停恢复，不计入。

因此不能把“11 次运行调用”“2 个 OCR 请求表达式”“多处业务调用入口”混成一个数字。

区域为屏幕逻辑点 `(x,y,width,height)`，设备 428×926 @3，竖屏。`CNRegion` 原代码采用 1284×2778 参考坐标，本表已经换算。全屏就是 `(0,0,428,926)`，不是“看了某个区域文字就等于区域 OCR”。涉及金额、账户的原文只保存在私有收据；这里列字段类别。

| 次数 / 功能块 / 观察 | 对应文件、行号与调用函数 | 触发条件、实际区域 | 识别内容、实际用途 | 必要性与处理 |

| 2 / 块1 / page-002 | `CNMiniTasks.m:610,643 navigateTo` → `refreshRegion:` → `CNTaskScreen.m:70` | 已测搜索栏 `(215,116.5)` 与小程序分类 `(39,172)` 点击后，检查终点；**(0,33.33,428,106.67)** | “搜索小程序”“搜索”，确认输入目标是原生小程序搜索框 | **可合并或用原生输入框命中替代**。搜索与分类点击已是固定坐标；当前 OCR 是输入前的安全检查。仅删检查会在未知弹窗/错误页输入，不能当完成优化 |

这里 8 次中 **6 次全屏、2 次局部**。虽然块8代码写着 `refreshRegion`，实际命中了前次全屏缓存；它不是第3次局部 OCR。普通滑动、等待、日历入口点击没有 OCR。

## 下一步可落地优化与验收边界

1. **先减面积，不减业务证据**：#5/#7 裁个人中心标题+账户区；#6 裁日历标题+当日状态区；#8 裁微信导航/搜索区。依据已有页样本里的坐标确定 ROI，一次离线对照所有要读取的节点是否仍在范围。现有样本只有执行文字，不能伪造图色模板或图片推理时间。实现后可用一张既有真图做针对性 ROI 测试；不因 UI 修改跑完整签到。
2. **#2 与 #3合并，目标正常预算7次**：在已验证布局上用原生点查询确认可编辑搜索框，执行固定点位/输入，然后只识别结果卡；旧观察不足或 AX 过期时仍执行 #2 OCR。先给搜索入口做本地回归，不重新探索整个微信。
3. **#4 与 #5合并，目标正常预算6次**：在录制的目标首页有可靠图片/元素身份门限时，直接固定点“我的”，一次账户 OCR 同时验身份、登录和动态数据；未知协议弹窗进入纠错分支。未经模板和异常门限验证，不默认跳过 #4。
4. **#1/#3/#8可逐步用本地图色或新鲜 AX 替代**，前提是设备确有对应能力、模板绑定版本/分辨率、正负页面区分经过验证。当前只确认了截图、原生点查询和 OCR，没有现成图色 API；图片比较即使不耗 Token 仍有截图与匹配成本，不能无测量地声称一定更快。
5. #5/#6/#7 的动态值与真实回执保留。用户要求最终余额时不能靠固定坐标“读取”值，更不能把点击当成功。账号、钱数、截图与日志留私有；公共 Skill 只存规则。

以上 7/6 是候选设计预算，不是已经测得的完成数字。本次只交付悬浮球改造、离线追溯工具和 Skill 策略，业务脚本保持已验证的8次路径。

## 离线复用命令

在已回传的运行目录上执行，不连接手机、不截图、不调用 OCR/AI：

```sh
python3 host/autodam_link/ocr_audit.py "$PRIVATE_RUN_DIRECTORY" --run-id "$RUN_ID"
```

输出只有计数、步骤、观察范围和时间，不含 OCR 文本、账户或金额。解释每次用途时结合该版本源码与必要的私有页面，不凭输出宣称拥有运行时调用栈。
